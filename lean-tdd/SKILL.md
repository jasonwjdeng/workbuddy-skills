# Lean TDD — 先红，后绿

**铁律：没有先失败的测试，就不写生产代码。** 已经写了？删掉，重来——不留"参考"、不"改写"、不看它。删掉就是删掉。

## 技术栈检测（开工前，一次性）

扫描项目根目录的栈标记（`pom.xml`/`build.gradle` → Java；`pyproject.toml`/`requirements.txt` → Python），命中则读取 `references/` 下对应的栈参考文件（如 `java-spring-boot.md`、`python-quant.md`）并应用其中的约定。未命中任何栈 → 跳过本步，只用通用规则。**项目的 AGENTS.md 约定优先级高于栈参考。**

## 循环

```
RED（写失败测试）→ 看红 → GREEN（最小实现）→ 看绿 → REFACTOR（保持绿）→ 下一个
```

### RED — 写失败测试

一次一个行为，命名说清意图，尽量用真实代码（mock 只在外部副作用不可避免时用）。先写断言再写其余。

### 看红（必做，不许跳）

跑这个测试，确认：

- 它是 **fail**（断言失败），不是 error（写错了）
- 失败原因正是"功能还不存在"，不是笔误
- **一写就绿？** 说明在测已有行为——改测试

### GREEN — 最小实现

写恰好让测试通过的最简代码。不顺手加功能、不顺手重构、不做"顺便优化"（YAGNI）。

### 看绿（必做）

本测试过 + 其他测试不挂 + 输出干净（无 error/warning）。别的测试挂了，立刻修。

### REFACTOR — 只在绿了之后

消重、改名、抽 helper。保持全绿，不加行为。然后进入下一个 RED。

## 好测试三原则

| 原则 | 好 | 坏 |
|------|----|----|
| 单一 | 一个行为 | 名字里有 "and" —— 拆开 |
| 清晰 | 名字描述行为 | `test('test1')` |
| 断言真实行为 | 断言被测代码的输出 | 断言 mock 被调了几次 |

## 例外

一次性原型、生成代码、纯配置文件可以不 TDD——**但必须先问用户**。"就这一次先不测"是合理化，不是例外。

## 卡住了

| 问题 | 解法 |
|------|------|
| 不知道怎么测 | 先写你期望的 API，先写断言；还不行就问用户 |
| 测试太复杂 | 设计太复杂。简化接口 |
| 什么都要 mock | 耦合太紧。上依赖注入 |
| setup 巨大 | 抽 helper；还复杂就是设计该简化 |

## Red Flags（全部意味着：删代码，重来）

| 念头 | 现实 |
|------|------|
| "太简单不用测" | 简单代码也会坏。测试 30 秒 |
| "之后再补测" | 后写的测试一跑就绿，证明不了任何事——你没看它红过，就证明不了它能抓住 bug |
| "已经手动测过了" | 手动测试无记录、不可重跑、压力下漏边界 |
| "先探索一下再写" | 可以。探索产物扔掉，然后 TDD |
| "删了 X 小时的代码太浪费" | 沉没成本。真选择是：TDD 重写（可信）vs 保留后补测（不可信） |
| "留着当参考" | 你会照着它改——那就是后补测试。删掉就是删掉 |
| "TDD 是教条，我要务实" | TDD 才是务实路径：提交前抓 bug、防回归、重构不慌 |

## 完成清单

- [ ] 每个新函数/方法都有测试
- [ ] 每个测试都亲眼看过红（且红的原因正确）
- [ ] 每处实现都是让测试变绿的最小代码
- [ ] 全部测试绿，输出干净
- [ ] 边界与错误路径已覆盖

勾不齐 = 跳了 TDD。重来。
