# Lean Design — 轻量设计前置

## 调用层级

本 skill 是**编排类（user-invoked）**：只在用户明确要求时启动。任务看起来适合但用户没点名时，先问一句"要走 lean-design 吗？"，不自动开始追问。编排类可调用纪律类 skill（lean-tdd / lean-debug / lean-review）；纪律类不会反向调用本 skill。

写代码之前，先完成一次快速对齐。全程遵循两条铁律：

1. **审批门只停一次**：呈现设计 → 用户明确同意 → 才动手。没有第二次停顿。
2. **仪式随任务缩放，审批不缩放**：小任务可以只有两句话的设计，但必须被确认。

## 第一步：分类（先宣布，可被否决）

动手前先给任务定级，并**说出来**让用户可以纠正：

- **Spike（探针）**：可行性问题（"能不能…"、"先试试…"）。产出是答案不是代码。2-3 句话说清要试什么，用户点头即查。产出的任何代码都标记为一次性。
- **Bounded（有界）**：改的是**这个仓库里已存在的流程**（加个开关、小接口、单文件修复）。没有现成流程可改的不算 bounded。
- **Architectural（架构）**：新项目、新子系统、改组件间接口或别人依赖的行为。

拿不准时取重的一档。**棘轮单向**：中途发现隐藏复杂度，立刻停下宣布升档；没有降档。

## 第二步：批量澄清（bounded 与 architectural）

**领域问题库（可选）**：检测项目技术栈（`pom.xml`/`build.gradle` + k8s 清单或 Spring 依赖 → `references/k8s-spring.md`；vectorbt/pypfopt/akshare 等 → `references/quant.md`），命中则把对应问题库作为候选前沿——按任务选用，不必全问。

把设计决策建模为**决策树**，每轮只问"前沿"——前置决策已就绪、现在就能问的问题。规则：

- **一轮问完整个前沿**。每题编号，并**附上你的推荐答案**（用户的任务是判断推荐对不对，不是从零想答案）。
- **事实自己查，决策留给用户**：需要看文件、跑命令、查文档的问题，自己去查，不拿去问用户。正在查的事实只阻塞依赖它的下游问题，其余照问。
- 用户答完一轮，重算前沿，问下一轮。**前沿清空 = 共识达成**，不许有任何"默认就这样吧"的未决分支。

```
❓ Q1 - <标题>：<问题正文，可含选项>
➡️ 推荐：<你的答案 + 一句理由>

❓ Q2 - …
➡️ 推荐：…
```

## 第三步：呈现设计（一次性）

前沿清空后，**一条消息**呈现完整设计，按任务级别取深度：

- **Bounded**：几句话——改什么文件、什么思路、怎么验证。
- **Architectural**：覆盖架构、组件、数据流、错误处理、测试各一小节；如有多个合理方案，给 2-3 个带权衡的选项 + 明确推荐（用户偏好编号选择）。

然后**停下等确认**。用户说 yes 才动手；有异议就改了再呈现一次。呈现设计和动手写代码不允许出现在同一口气里。

## 第四步：收尾

- **Spike**：报告结论（推荐 + 依据），代码标注一次性。
- **Bounded**：确认后直接进入正常开发流程（测试先行）。
- **Architectural**：默认不写设计文档，直接开工；仅当用户要求（或项目有 spec 约定）时才落 `docs/specs/YYYY-MM-DD-<主题>-design.md` 并提交。

不强制交接任何后续流程。

## Red Flags

| 念头 | 现实 |
|------|------|
| "太简单了，直接做" | 简单意味着设计只有两句话，不是没有设计 |
| "我先开始做，用户在看方案" | 呈现 ≠ 批准。停下 |
| "分节给用户确认更稳" | 审批门只停一次。整条消息呈现，一次确认 |
| "这个事实问用户最快" | 事实自己查。用户只做决策 |
| "差不多了，剩下的边做边定" | 前沿没清空就是没对齐。问完再动 |
| "变复杂了，但快完了" | 停下，升档，宣布 |
