# Lean Review — 先证据，后结论

## 调用层级

本 skill 是**纪律类（model-invoked）**：声称完成/提交前自动生效，无需用户点名。不主动启动编排类 skill（lean-design / lean-implement）——评审发现需求级缺口时，如实报告，由用户决定是否回到设计流程。

**铁律：没有刚跑的验证命令输出，不许说"好了/通过了/修好了"。** 信心 ≠ 证据。

## 技术栈检测（评审前，一次性）

扫描项目根目录的栈标记（`pom.xml`/`build.gradle` → Java；`pyproject.toml`/`requirements.txt` → Python），命中则读取 `references/` 下对应的栈检查清单（如 `java-spring-boot.md`、`python-quant.md`），按其中的 ⚠️/◆/· 预分级逐项核对。未命中 → 跳过。项目 AGENTS.md 约定优先。

## 门函数（任何完成类声称前）

```
1. 识别：哪条命令能证明这个结论？
2. 跑：完整跑一遍（新的、全量的，不是上次的结果）
3. 读：看全输出、exit code、失败计数
4. 对照：输出真的支持结论吗？——不支持就如实报告实际状态
5. 只有之后：带着证据下结论
跳任何一步 = 撒谎，不是验证。
```

## 声称与证据对照

| 声称 | 需要的证据 | 不够的 |
|------|-----------|--------|
| 测试通过 | 测试命令输出 0 失败 | 上次跑过、"应该能过" |
| 构建成功 | 构建命令 exit 0 | linter 过了（linter 不查编译） |
| bug 修好 | 原始症状命令现在过 | 代码改了（改 ≠ 修） |
| 回归测试有效 | 红绿回环验证过 | 测试跑过一次绿了 |
| agent 完成 | 自己看 VCS diff 核实 | agent 自述"成功" |
| 需求达成 | 逐条核对需求清单 | 测试全绿（绿 ≠ 需求齐） |

**回归测试红绿回环**：写测试 → 跑（过）→ 回退修复 → 跑（必须红）→ 恢复修复 → 跑（过）。缺中间两步的"回归测试"不可信。

## 提交前评审（commit / PR 前）

对着**原始需求或设计**做两轴评审，一条消息输出，按严重度排序：

1. **合规轴**：diff 是否忠实实现了需求/spec？逐条核对，报告缺口。
2. **质量轴**：是否违反项目约定与常识（错误处理、安全、命名、测试覆盖）？

分级报告：**Critical**（阻塞，不解决不提交）/ **Major**（建议本次解决）/ **Minor**（可留 follow-up）。只报告真实发现，不凑数。

## 适用时机（永远）

在任何以下动作之前：成功/完成类措辞、表达满意（"搞定了！"）、commit、push、建 PR、标任务完成、派子 agent 之后的验收。规则覆盖原话、同义改写和一切暗示成功的表述。

## Red Flags

| 念头 | 现实 |
|------|------|
| "应该没问题" | 跑验证 |
| "我有信心" | 信心 ≠ 证据 |
| "就这一次" | 没有例外 |
| "linter 过了" | linter ≠ 编译器 |
| "agent 说成功了" | 独立核实 diff |
| "局部检查够了" | 局部证明不了整体 |
| "累了，想收工" | 疲劳不是豁免理由 |
