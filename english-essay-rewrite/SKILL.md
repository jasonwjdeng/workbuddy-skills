# English Essay Rewrite — 英语写作批改与语体改写

## 用途

对用户的英语习作做三件事，缺一不可：

1. **批改**：定位语法、搭配、语用错误，并说明"为什么错、正确形式是什么"。
2. **改写**：保持核心信息完全不变，产出两个语体版本——正式书面语（formal / written）与自然口语（casual / spoken）。
3. **沉淀**：附上逐条修改理由、重点词汇短语搭配清单、迁移练习。

学习者从"错在哪"和"两种语体怎么切换"中获益，而不是拿到一段被直接替换过的文字。

## 触发场景

- "批改我的英语作文 / 帮我改改这段英文"
- "生成正式版和口语版"
- "draft 目录里有我写的短文……"（写作练习工作流）
- 要求解释某段英文草稿的用词、句式、语体问题

## 目录约定

读写目录由用户的工作区决定，默认约定：

| 目录 | 用途 |
| --- | --- |
| `draft/` | 用户的原稿（只读，绝不覆盖、绝不修改） |
| `output/` | 产物输出目录 |

若用户未指定目录，先在工作区内查找 `draft/`；找不到再询问。若工作区没有该约定，直接用用户给出的路径。

**输出文件命名**：沿用原稿文件名，追加语体后缀。

```
draft/20260924-application-i-am-working-on.md
  → output/20260924-application-i-am-working-on-formal.md
  → output/20260924-application-i-am-working-on-casual.md
```

原稿若无 `YYYYMMDD-` 前缀，则沿用原名加后缀，不擅自补日期。

## 执行流程

### 步骤 1：定位并完整读取原稿

1. 用 Glob 找 `draft/*.md`（或用户指定路径）。若有多篇，列出让用户选，不要猜。
2. 完整读取原稿。**不修改原稿**，一个字都不改。
3. 先盘一遍：作者想表达的核心信息有哪几条？把这些信息点列成清单（后面用来校验两版是否都覆盖）。

### 步骤 2：错误诊断

逐句过一遍，按三类归档：

- **语法/形式错误**：冠词、单复数、时态、主谓一致、并列结构不平行。
- **搭配/用词错误**：介词搭配（`composed by` → `be composed of`）、数量表达（`tens of` → `dozens of`）、领域术语误用（`mode` → `configuration`）。
- **语用/中式英语**：字面对译、修饰语顺序（`software backend engineer` → `backend software engineer`）、逻辑主被动错位（系统"自己部署自己"）。

高频错误清单见 `references/common-errors.md`，诊断时对照扫描，尤其注意冠词与介词搭配——中文母语者最易失分处。

### 步骤 3：产出两个改写版本

同一份信息，两种语体。**两版的信息点必须完全对等**，只允许语体层面的差异。

- 正式版：见 `references/register-matrix.md` 的「正式书面语」列。要点是无缩略形式、主动/被动分工明确、名词化、从句与分词短语焊接短句、措辞升格。
- 口语版：见同文件的「自然口语」列。要点是缩略形式、话语标记（so / basically / a bit）、短语动词、第一人称 We 视角、短句并列、词汇下沉。

**硬性约束**：

- 不添加原稿没有的信息，不做事实性延伸。例如原稿说 on-premises，就不要顺势写成 "not in the cloud"。
- 不删除原稿的信息点。改写后逐一核对步骤 1 的信息点清单。
- 技术专有名词不翻译、不降格（保留 Kubernetes / Spring Boot / Helm 等），只放松其外围表述。
- 正文用英文，修改理由与词汇讲解用中文（面向中文母语学习者）。

### 步骤 4：组织交付文件

按 `references/output-template.md` 的结构写，四段式：

1. `## Rewritten Text` — 改写正文
2. `## 修改理由说明` — 分「共同性修正」表格 + 「语体层面的选择」编号列表 +（可选）「事实性存疑」
3. `## 重点词汇、短语及常用搭配` — 分类表格，含释义与搭配/例句
4. `## 迁移练习` — 3 条，让学习者用自己的情况复写

修改理由表格的列固定为：`原文 | 问题 | 修正`。每条都要点出**问题类型**，不能只给答案。

**关于可选第三节「事实性存疑」**：原稿若出现**技术事实错误**（而非语言错误），按以下方式处理——

- 正文中**按原意保留**，不擅自改技术事实。批改的职责边界是语言。
- 在「事实性存疑」小节里点名：更准确的表述是什么、为什么、并反问用户想表达哪一个。
- 没有存疑之处就省略整节，不要为凑结构而写。

### 步骤 5：校验

两个文件写完后跑校验脚本：

```bash
<python> scripts/check_rewrite.py <output-dir> --source <draft-file>
```

脚本检查：命名是否正确、四个必需章节是否齐全、**正式版是否混入缩略形式**（`don't` / `it's` / `I'm` 等，最常见的语体泄漏）、口语版是否确实具备口语特征（缩略形式出现次数 + 话语标记种类）。

关于缩略形式的判定边界（写脚本时踩过的坑）：

- **算缩略**：`here's` / `it's` / `we're` / `don't`，以及**名词 + `'s` + 分词/介词**这一类（`the data's in`、`the app's built on Java`）——后者的 `'s` 是 is/has 的缩略，口语里极常见，早期版本漏检过。
- **不算缩略**：属格（`the customer's portfolio`、`the system's performance`）。属格在正式写作中完全合法，误报会让这个检查失去可信度，所以判定靠 `'s` 后面的词性——跟名词算属格，跟介词/副词/分词算缩略。
- 句首的 `So` 只在句首位置算口语标记，正式的 `so that` / `so as to` 必须放行。

改动脚本后**必须对已有产物做回归测试**（`for s in ...; do check_rewrite.py output --source draft/$s.md; done`），并用"往正式版里塞缩略形式 + 往正式版里塞属格"这一正一负两个用例验证判定边界。

校验不通过就改，不要带着告警交付。

### 步骤 6：呈现

调用 present_files，把**正式版在前、口语版在后**（正式版信息密度更高，先看它更容易建立结构感）。

文字回复里给：两版的核心差异机制（各 2–3 条）、原稿最值得记住的语言点 3–6 条、以及一句可选的后续动作（如"要不要读给你听"→ 转 `read-aloud-audio` skill）。

## 常见陷阱

- **改写而不是重写**：口语版不是"把正式版再翻一遍"，两者都要从原稿出发。
- **过度纠正**：作者的个人语气与选词习惯要保留，只改错、不改成"标准范文"。
- **术语失真**：技术名词被"口语化"到看不懂，比不口语化更糟。
- **越界改技术事实**：API 名称、标准名称、端口号、组件职责属于技术事实。正文按原意保留，只在「事实性存疑」小节提示——擅自"改正"会让学习者失去一个发现问题的机会，也容易改错。
- **理由空泛**："更地道""更正式"这类评语没有信息量。要说清机制，例如"并列不平行：be 动词与现在分词不能并列"。
- **两版信息不对等**：写完必须回头核对信息点清单。
