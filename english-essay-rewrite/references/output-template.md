# 交付文件模板

两个输出文件使用同一骨架，只有标题、副标题与正文内容不同。**章节标题保持英文原文，便于校验脚本与后续自动化识别。**

````markdown
# <英文标题> — 正式书面语版 | 自然口语版

> 源文件：`draft/<原稿文件名>`
> 改写版本：Formal / Written Register  |  Casual / Spoken Register
> 生成日期：YYYY-MM-DD

---

## Rewritten Text

<改写后的英文正文，段落结构与原稿对应>

---
````

## 填写规范

**标题行**：英文标题用原稿主题的英文名（由原稿内容提炼，不加引号）；破折号后标注语体。

**修改理由说明 · 共同性修正表**：

- 三列固定为 `原文 | 问题 | 修正`，顺序不能变。
- "问题"列必须写机制，不能只写"不地道"。反例："搭配不当"；正例："compose 表'由…组成'时只接 of，by 用于施动者"。
- 表格按错误类别分组排序（冠词 → 搭配 → 数量 → 并列 → 主被动 → 术语），便于学习者看出自己的集中失分点。
- 只列实际出现在原稿里的问题。**不要凑条目**。

**修改理由说明 · 语体层面的选择**：

- 每个版本 5–7 条，每条一个维度，编号列表。
- 每条格式：`**维度名**：做法 + 取自本稿的例子`。

**修改理由说明 · 事实性存疑（可选第三节）**：

- 只在原稿出现**技术事实错误**或**表述边界模糊**时写这一节，语言错误一律放第一节的表格里。
- 两类适用情形：
  - **技术事实存疑**：把 A 的标准说成 B 的标准、URL 缺端口、版本号与特性不匹配、把某个能力归给了错误的组件。
  - **表述边界模糊**：指代范围不清（如 "outside the bank" 到底是网络边界还是组织边界）。这类不是错误，只是可能被读者理解成别的意思。
- 原则：**批改只负责语言，不擅自改技术事实**。存疑的说法在正文里按原意保留，但在这一节点名，给出更准确的表述，最后反问用户想表达的是哪一个；补全信息（如给 the bank 补成 the bank's network）属于信息补充，须由用户确认。
- 没有存疑之处就整节省略，不要为了凑结构而写。

**表格的边界**：第一节的表格只列**真实错误**。像"时态链分工是否一致"这类整体自检，若结论是"原稿处理得当"，就不要伪装成错误塞进表格——可写成表格末行并注明这是自查结论，或直接省去。

**重点词汇表**：

- 按语义分组，通常 2–3 组（如"身份与职责""系统与技术描述""加分句式"）。
- "用法与搭配"列要给出**可复制的片段**（搭配对象、常见共现词、例句），而不是抽象描述。
- 至少收录原稿中出现的关键词，可补充同类高频词。

**迁移练习**：固定 3 条，每条指定一个目标结构 + 一个写作场景，让学习者用自身经验复写。

## 一个真实片段（供对照语气密度）

```markdown
| composed by | 搭配错误，compose 表"由…组成"只接 **of** | **comprises**（或 be composed **of**） |
| tens of microservices | tens of 只用于 tens of thousands 等大数 | **dozens of** microservices（"几十个"） |
| running on a on-premise Kubernetes | ① on-premise 应为形容词 **on-premises**；② 以元音音素开头，冠词用 **an**；③ Kubernetes 是集群，需补 cluster | runs on **an on-premises Kubernetes cluster** |
```
