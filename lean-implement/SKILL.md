# Lean Implement — 照计划做，阻塞就问

## 调用层级

本 skill 是**编排类（user-invoked）**：只在用户拿着计划/设计明确要求执行时启动。可调用纪律类 skill（收尾必须进 lean-review；写码过程走 lean-tdd）；纪律类不会反向调用本 skill。

**开场声明**："我正在按 lean-implement 执行这份计划。"

## 铁律

1. **不在 main/master 上直接开工**，除非用户明确同意。
2. **计划有疑问先提，不带着疑虑开工。**
3. **阻塞就停下问，不许猜。** 猜测式推进 = 返工。

## 第一步：批判性读计划

- 通读计划/设计文件，找出疑问、缺口、与现状的矛盾
- 有疑问：列给用户，**等回答再动手**
- 无疑问：把任务逐项建为 todo，开工

## 第二步：逐任务执行

对每个任务：

1. 标记 in_progress
2. **按计划步骤照做**，不即兴改步骤（发现计划有问题 → 回到"停下问"）
3. 跑计划指定的验证命令
4. 验证过 → 标记 completed（**逐个标记，不许攒到最后批量打钩**）

跳过指定验证 = 任务没完成。

## 第三步：收尾

全部任务完成且验证过后，进入验证与评审流程（lean-review）：先跑全量验证拿证据，再按严重度评审 diff，然后才谈提交。

## 何时停下问（不是猜）

- 遇到阻塞：缺依赖、测试失败、指令看不懂
- 计划有致命缺口，根本无法开始
- 验证反复失败
- 发现计划的方向本身要重想

用户根据你的反馈更新了计划 → 回到第一步重新批判性读。**不要硬闯阻塞。**

## Red Flags

| 念头 | 现实 |
|------|------|
| "计划大概懂了，先干着" | 有疑问先问。带着疑虑开工是浪费 |
| "这一步可以优化掉" | 照做。要改计划，先问用户 |
| "全做完再统一标记" | 逐个标记。批量打钩 = 藏住中途失败 |
| "验证跳了，下一步反正会测" | 跑指定验证。跳过即未完成 |
| "main 上改快一点" | 先拿用户同意 |
| "卡住了，先绕过去试试" | 停下问。绕过阻塞是给自己埋雷 |
